# Worktree並列開発環境 CLIツール設計計画

## 概要

Git Worktreeを使った並列開発で、docker composeの固定ポート問題を解決するCLIツール「gwt」を設計する。

### 背景・課題

- Claude CodeなどのCLI AIエージェント活用でGit Worktreeを使った並列開発が盛んになっている
- 一部プロジェクトではdocker composeが複数サービスを固定ポートでホスト側に露出
- 複数ワークツリーで同時並列に動作確認することが困難

### 目標

- 各ワークツリーで独立してdocker composeを起動可能にする
- Playwright + Claude Codeでの動作確認をサポート
- 簡単に設定できるツールを提供

## 要件まとめ

| 項目 | 内容 |
|------|------|
| 並列度 | 4-5ワークツリー同時稼働 |
| 環境 | Windows 11 22H2 + Docker Desktop / macOS / Linux |
| compose変更 | オーバーライドファイル活用（既存yml変更不要） |
| ルーティング | ポートベース（クロスプラットフォーム対応） |
| 成果物 | CLIツール（uvx対応） |

## ポート割り当て戦略

```
ワークツリーインデックス (0-9) × サービス
- WTインデックス0: web=8000, api=8100, db_admin=8200, ...
- WTインデックス1: web=8001, api=8101, db_admin=8201, ...
- WTインデックス2: web=8002, api=8102, db_admin=8202, ...
```

設定例:
```yaml
services:
  web: base_port=8000
  api: base_port=8100
  pgadmin: base_port=8200
```

## CLIコマンド仕様

### `gwt init`
プロジェクトにgwt設定を追加
```bash
gwt init
# → .gwt/config.yml 作成
# → docker-compose.override.gwt.yml 生成
```

### `gwt up [name]`
ワークツリー環境を起動
```bash
gwt up feature-branch
# → 空きインデックスを割り当て
# → COMPOSE_PROJECT_NAME=project-feature-branch
# → 動的ポートで起動
# → アクセスURL表示
```

### `gwt down [name]`
ワークツリー環境を停止
```bash
gwt down feature-branch
# → コンテナ停止・削除
# → インデックス解放
```

### `gwt list`
稼働中の環境一覧
```bash
gwt list
# NAME            INDEX  WEB      API      STATUS
# feature-branch  1      :8001    :8101    running
# bugfix-123      2      :8002    :8102    running
```

### `gwt url [name] [service]`
アクセスURLを取得
```bash
gwt url feature-branch web
# http://localhost:8001

gwt url feature-branch --all
# web: http://localhost:8001
# api: http://localhost:8101
```

### `gwt playwright [name]`
Playwright用の情報表示
```bash
gwt playwright feature-branch
# BASE_URL=http://localhost:8001
# API_URL=http://localhost:8101
```

## 設定ファイル構造

### `.gwt/config.yml`（プロジェクト設定）
```yaml
version: "1"
project_name: my-project

services:
  web:
    container_port: 3000
    base_host_port: 8000
  api:
    container_port: 5000
    base_host_port: 8100
  pgadmin:
    container_port: 80
    base_host_port: 8200

# オプション: サブドメイン対応
subdomain:
  enabled: false
  domain: project.local
```

### `.gwt/state.json`（実行時状態）
```json
{
  "instances": {
    "feature-branch": {
      "index": 1,
      "started_at": "2024-01-07T10:00:00Z",
      "ports": {
        "web": 8001,
        "api": 8101
      }
    }
  }
}
```

### `docker-compose.override.gwt.yml`（自動生成）
```yaml
version: "3.8"

services:
  web:
    ports:
      - "${GWT_WEB_PORT:-8000}:3000"

  api:
    ports:
      - "${GWT_API_PORT:-8100}:5000"

networks:
  default:
    name: gwt-${GWT_PROJECT_NAME:-default}
```

## 実装計画

### Phase 1: 基盤実装
1. プロジェクト構造作成（Python + typer）
2. 設定ファイル読み書き
3. ポート管理ロジック

### Phase 2: compose統合
4. docker-compose操作（docker-py or subprocess）
5. オーバーライドファイル生成
6. up/down/list実装

### Phase 3: 利便性向上
7. url/playwrightコマンド
8. 自動検出（現在のワークツリー名）
9. エラーハンドリング強化

### Phase 4: ドキュメント・配布
10. README作成
11. 使い方ガイド
12. PyPI公開 or uvx対応

## 実装言語・ツール

- **言語**: Python 3.11+
- **CLI**: typer
- **YAML**: PyYAML or ruamel.yaml
- **Docker**: docker-py or subprocess
- **配布**: uv (uvx gwt で実行可能)

## 既存プロジェクトへの変更

既存docker-compose.ymlの変更は**不要**。以下を追加するのみ：
1. `.gwt/config.yml` - gwt設定
2. `.gwt/state.json` - 実行時状態（.gitignore推奨）
3. `docker-compose.override.gwt.yml` - ポート設定オーバーライド

## 補足事項

### 採用しなかったアプローチ

#### 仮想化（Multipass/Lima等）
- **却下理由**: WSL2との互換性問題（Multipassは非互換、Limaは実験的）
- **リソースオーバーヘッド**: 4-5並列でVMを立てるとメモリ消費が大きい
- **代替**: ポートベースの分離で十分な隔離が可能

#### サブドメインベースルーティング
- **保留理由**: hostsファイル編集が必要でクロスプラットフォーム展開が複雑
- **将来対応**: オプションとして実装可能（`subdomain.enabled: true`）

#### Traefik共有インスタンス
- **保留理由**: 追加コンポーネントの管理が複雑
- **代替**: ポートベースなら追加コンポーネント不要

### 設計上の決定事項

| 決定 | 理由 |
|------|------|
| ポートベースを基本 | hostsファイル編集不要、クロスプラットフォーム |
| オーバーライドファイル | 既存compose.ymlを変更しない |
| Python + typer | uvx対応、クロスプラットフォーム |
| 状態管理はJSON | シンプル、人間可読 |

## 崩壊条件（この設計が破綻するケース）

### 1. ポート枯渇

**条件**: 同時稼働数がポートレンジを超える

- 現設計: インデックス0-9で10ワークツリーまで
- サービスが10個以上あると、ポートレンジが重複する可能性

**対策案**:
- base_portのレンジを広げる（8000-8099, 8100-8199, ...）
- 動的ポート割り当て（空きポートを自動検出）

### 2. 複数マシンでの状態不整合

**条件**: 同一プロジェクトを複数マシンで並列開発

- state.jsonがマシンごとに独立
- 同じインデックスを複数マシンで使用するとポート競合

**対策案**:
- マシン識別子をインデックスに組み込む
- 中央集権的な状態管理（Redis等）- 実用上は稀なケース

### 3. compose.ymlに ports が定義されていない

**条件**: 既存compose.ymlでportsがなく、内部通信のみ

- オーバーライドでports追加は可能だが、サービス名の把握が必要
- `gwt init`時に対話的に設定が必要

**対策案**:
- compose.yml解析でサービス一覧を取得
- ユーザーに公開するサービスを選択させる

### 4. Docker Composeのバージョン非互換

**条件**: 古いdocker-compose（v1）を使用

- `docker compose`（v2）前提の設計
- v1では`docker-compose`コマンドが必要

**対策案**:
- 起動時にバージョンチェック
- v1対応のフォールバック

### 5. WSL2とWindowsでの同時アクセス

**条件**: WSL2内のgwtとWindows側から同時にアクセス

- WSL2 NATモードではlocalhostポートフォワーディングに制限あり
- ミラーモード（Win11 22H2+）なら問題なし

**対策案**:
- WSL2ミラーモードを推奨
- Windows側からはWSL2のIPアドレスでアクセス

### 6. 既存のdocker-compose.override.ymlとの競合

**条件**: プロジェクトに既存のoverride.ymlがある

- Docker Composeは自動的にoverride.ymlを読み込む
- gwt用のoverride.gwt.ymlと競合する可能性

**対策案**:
- `-f`オプションで明示的にファイル指定
- `docker compose -f docker-compose.yml -f docker-compose.override.gwt.yml up`

### 7. コンテナ内からの相対URL

**条件**: アプリケーションがコンテナ内で絶対URLを生成

- 例: APIがレスポンスに`http://localhost:5000/...`を含む
- ポートが変わると不整合

**対策案**:
- 環境変数でベースURLを注入（`PUBLIC_URL`等）
- アプリ側でリバースプロキシ対応設計が必要

### 8. ボリュームの競合

**条件**: 複数ワークツリーで同じボリューム名を使用

- COMPOSE_PROJECT_NAMEでネットワークは分離される
- 明示的なボリューム名（`volumes: db_data:`）は共有される可能性

**対策案**:
- プロジェクト名プレフィックスをボリュームにも適用
- オーバーライドでボリューム名を動的化
