# WSL2環境での軽量仮想化オプション調査

## 調査目的

Git Worktree並列開発でdocker composeのポート競合を解決するため、仮想化による隔離の選択肢を調査。

## 調査結果サマリー

| オプション | WSL2互換性 | 推奨度 | 備考 |
|-----------|-----------|--------|------|
| Multipass | ❌ 非互換 | 非推奨 | Hyper-Vネットワーク分離問題 |
| Lima | ⚠️ 実験的 | 要検討 | WSL2 VMタイプは動作するが制限多数 |
| Hyper-V直接 | ✅ 最適 | 推奨 | ネットワーク設定の完全制御 |
| Podman Machine | ✅ 安定 | 推奨 | Hyper-Vベース、コンテナ中心 |

---

## 1. Multipass のWSL2対応状況

### 状況: **WSL2とは非互換** ❌

#### 根本的問題
- MultipassはVirtualBoxまたはHyper-Vを使用
- WSL2（Hyper-V上）と同時使用時にネットワーク分離が発生

#### 具体的な制限
- WSL2とMultipassは異なるHyper-V仮想ネットワークスイッチを使用
  - WSL: `vEthernet (WSL)`
  - Multipass: `vEthernet (Default Switch)`
- 両者間の通信不可
- VirtualBoxはHyper-Vと互換性がないため、VMP有効時に動作不可

#### 結論
WSL2環境ではMultipassの使用は推奨されない

---

## 2. Lima のWindows/WSL2対応状況

### 状況: **部分的にサポート** ⚠️ （実験的）

#### WSL2 VMタイプの要件
- Lima 0.18以上が必須
- Windows 10 Build 19041以上、またはWindows 11
- Windows ネイティブの `wsl.exe` を活用

#### 設定例
```bash
limactl start --vm-type=wsl2 --mount-type=wsl2 --containerd=system
```

#### 主な制限事項
- **実験的機能**: 将来的な仕様変更の可能性あり
- **TARフォーマット必須**: 通常のVMイメージではなくrootfs tar形式が必要
- **ツール不足**: Windowsにはssh.exe、gzip.exeなどがないため、MinGit必須
  ```bash
  winget install -e --id Git.MinGit
  ```
- **カーネルログ欠落**: シリアルログにカーネルブート情報が含まれない
- **オプション互換性制限**: 使用可能な設定が限定的

#### 結論
試験的用途には可、本番環境は推奨されない

---

## 3. Hyper-V直接利用

### 特性
- Windows 11 Pro/Enterprise標準装備のネイティブハイパーバイザー
- 最小オーバーヘッド
- WSL2との共存可能

### 利点
- ネットワーク設定の完全な制御
- 複数VM管理が安定

### 欠点
- UI/CLIが基本的、管理ツール必須
- VMの作成・管理に手間がかかる

### 推奨用途
複数VMを安定的に管理する必要がある場合

---

## 4. Podman Machine on Hyper-V

### 特性
- WSL2以外にHyper-Vオプションを提供
- コンテナ中心（VM中心ではない）
- Hyper-Vベースで高いネットワーク柔軟性

### 利点
- Docker互換のコンテナワークフロー
- ネットワーク設定が柔軟

### 推奨用途
Docker/Podmanベースのコンテナワークフロー

---

## 5. その他の選択肢

### Vagrant + Hyper-V
- WSL2でのネットワーク課題が報告されている
- Hyper-Vプロバイダーの使用がより安定

### Firecracker
- **Windows対応**: 非対応（Linux専用）
- WSL2内でLinuxとして動作可能だが、ネストハイパーバイザー制限あり

## ネットワーク設定の柔軟性比較

| オプション | NAT | ミラーモード | 静的IP | DNS設定 | VPN互換性 |
|-----------|-----|-----------|---------|--------|----------|
| WSL2 | ✅標準 | ✅(Win11 22H2+) | ⚠️スクリプト必須 | ✅dnsTunneling | ✅改善 |
| Hyper-V | ✅ | ✅ | ✅ネイティブ | ✅ | ✅高 |
| Multipass | ✅ | ❌ | ✅ | ✅ | △ |
| Lima/WSL2 | ✅ | ✅WSL2継承 | ⚠️ | ✅WSL2継承 | ✅WSL2継承 |

### WSL2のネットワーク強化点 (Windows 11 22H2以上)

- **ミラーモード** (`networkingMode=mirrored`): Windows ↔ WSL2で`localhost`直接接続可能
- **DNS Tunneling**: VPN互換性向上
- **Auto Proxy** (`autoProxy=true`): Windows プロキシ設定自動同期
- **IPv6サポート**: ミラーモード有効時

---

## 推奨構成

### WSL2を主軸とする場合
- ✅ **最適**: WSL2 + Docker Desktop/Podman (WSL2バックエンド)
- ⚠️ **要検討**: Lima on WSL2（実験的、監視必要）
- ❌ **非推奨**: Multipass

### 完全な隔離VMが必要な場合
- ✅ **最適**: Hyper-V + Vagrant/Podman Machine
- 理由: ネットワーク設定の完全な制御、複数VM管理の安定性

### ネットワーク柔軟性重視
- ✅ **最適**: WSL2 ミラーモード (Windows 11 22H2+)
- 代替: Hyper-V ネイティブ

---

## 本プロジェクトでの結論

**仮想化アプローチは採用しない**

理由:
1. MultipassはWSL2と非互換
2. Limaは実験的で本番利用に不安
3. Hyper-V直接は管理コストが高い
4. 4-5並列程度ならポートベースの分離で十分

代替アプローチ: **docker compose --project-name + 環境変数によるポート動的割り当て**
